## 1. プロジェクト概要

### 1.1 背景

Markdown は、技術文書・議事録・仕様書・ブログ下書き・学術メモなど、幅広い場面で日常的に用いられる軽量マークアップ言語である。しかし、作成した Markdown を体裁の整った配布用ドキュメントとして共有する際には、PDF への変換が必要になることが多い。現状、この変換には専用エディタの導入、コマンドラインツール（Pandoc 等）の習得、あるいは機能や広告の制約が大きいオンラインサービスの利用が求められ、いずれも一般ユーザーにとっては手間や学習コストが高い。

加えて、文書をオンライン変換サービスにアップロードすることへのプライバシー上の懸念や、日本語をはじめとする多バイト文字（CJK）のフォントが正しく埋め込まれず文字化け・字形崩れが起きるといった品質問題も、既存手段に共通する課題である。

本プロジェクトは、インストール不要でブラウザだけで完結し、入力からプレビュー、PDF 出力までを直感的な操作で行える変換ツールを提供することで、これらの課題を解消することを目的とする。

### 1.2 目的（達成すべきゴール）

本システムが達成すべき中心的な目的は、第一に、Markdown を書ける利用者であれば説明なしに数ステップで PDF を生成・ダウンロードできる、平易な操作体験を提供することである。第二に、コードハイライト、表、数式、図、日本語フォントなど実用上必要な要素を、崩れのない高品質な PDF として出力することである。第三に、利用者の文書を不必要に保持しない、プライバシーに配慮した設計とすることである。

### 1.3 スコープ

本書が対象とする範囲（イン・スコープ）は、Markdown の入力・編集・プレビュー、PDF への変換、出力体裁（ページ設定・テーマ・フォント等）の指定、生成 PDF のダウンロードである。

対象外（アウト・オブ・スコープ）として、本フェーズでは次を扱わない。すなわち、複数利用者によるリアルタイム共同編集、クラウド上での文書の永続保存・版管理、Markdown 以外の入力形式（Word 等）からの変換、PDF からの逆変換（PDF → Markdown）、課金・有料プランの本格的な実装である。これらは将来フェーズの候補として第15章に記載する。

## 2. システム概要

Matop は、ブラウザ上で動作する単機能特化型のWebアプリケーションである。画面は左に Markdown を入力するエディタ、右にリアルタイムのプレビューを配置した二分割構成を基本とする。利用者はテキストを直接入力するか、`.md` ファイルを読み込み、出力設定（用紙サイズ・余白・テーマ・フォント・ヘッダー/フッターなど）を選んだうえで、変換ボタンを押すことで PDF を生成しダウンロードする。

アカウント登録は不要とし、誰でも即座に利用を開始できることを基本方針とする。利用者の文書は変換処理に必要な範囲を超えて保持せず、処理完了後は速やかに破棄する。

---

## 3. 想定利用者とペルソナ

本システムの利用者は、Markdown を扱う一般の不特定多数のユーザーである。具体的には、技術文書やREADMEを整える開発者、議事録や報告書をまとめるビジネスパーソン、レポートやメモを整形する学生・研究者などが含まれる。デバイスは PC を主としつつ、スマートフォン・タブレットからの閲覧・軽微な編集にも配慮する。

代表的なペルソナとして、「GitHub で Markdown の README を書いているが、社内共有用に体裁の整った PDF が必要になった開発者」「Markdown でレポートを書き、提出用に PDF 化したいが LaTeX は使いこなせない学生」を想定する。いずれも Markdown の記法は理解している一方、コマンドラインツールや組版ソフトの習得には抵抗があるという共通点を持つ。

## 5. 利用フロー

### 5.1 現状（As-Is）の課題

現状、利用者が Markdown を PDF 化するには、専用エディタや拡張機能の導入、Pandoc などのコマンドラインツールの設定、あるいは制約の多いオンライン変換サービスの利用といった手段を採る必要がある。これらは導入・学習の負担が大きく、日本語フォントの埋め込み不良による文字崩れや、文書のアップロードに伴うプライバシー上の不安を伴いやすい。

### 5.2 あるべき姿（To-Be）

Matop では、利用者はブラウザでページを開き、Markdown を入力または読み込み、リアルタイムのプレビューで仕上がりを確認する。必要に応じて用紙サイズやテーマを選び、変換ボタンを押すと、体裁の整った PDF が生成されダウンロードされる。インストールやアカウント登録は不要であり、日本語も崩れずに出力される。この一連の操作は、説明を読まずとも完結できる平易さを目標とする。

## 7. 非機能要件

非機能要件として、システムが満たすべき品質水準を以下に定める。

**パフォーマンス**として、標準的な分量（おおよそ A4 で20ページ程度）の文書について、PDF 生成を5秒以内に完了することを目標とする。プレビューの更新は入力から200ミリ秒以内の体感即時性を目指す。大容量文書では進捗表示を行う。

**プライバシー・セキュリティ**は本プロダクトの重要要件である。利用者の文書内容は、PDF 生成に必要な範囲を超えて保持・記録しない。サーバー側で処理する場合も、文書はメモリ上で処理し、生成後ただちに破棄し、内容をログに記録しない。全通信は TLS で暗号化する。外部から読み込む画像 URL 等に起因するスクリプト実行を防ぐため、プレビュー描画時に入力をサニタイズする。ファイル読み込みはサイズ・形式を検証する。

**可用性**として、稼働率は月間99.9%以上を目標とする。クライアント側で完結する処理については、サーバー障害時も入力・プレビューが継続できることが望ましい。

**ユーザビリティ**として、初回利用者が説明を読まずに変換まで到達できることを基準とする。主要操作（入力・設定・変換）を一画面内に収め、変換完了までの操作を最小限とする。

**互換性**として、最新2バージョンの主要ブラウザ（Chrome、Safari、Edge、Firefox）に対応する。生成 PDF は一般的な PDF ビューアで正しく表示・印刷でき、本文テキストが選択・検索可能（ラスタライズしない）であることを要件とする。

**保守性・拡張性**として、Markdown パーサ、レンダリング、PDF 生成を疎結合に保ち、テーマやプラグインを追加しやすい構成とする。

**国際化**として、UI とドキュメントを多言語化可能な構造とし、特に日本語の組版（禁則処理・行間・約物）に配慮する。

## 8. 画面一覧・画面遷移

本システムは単一画面（シングルページ）を中心に構成する。主画面は、上部にツールバー（ファイル読み込み、設定、変換ボタン等）、左にエディタ、右にプレビューを配置する二分割レイアウトとする。出力設定はモーダルまたはサイドパネルで提供し、用紙サイズ・余白・テーマ・フォント・ヘッダー/フッターをまとめて指定できる。補助画面として、Markdown 記法ガイド、およびプライバシー方針の表示を持つ。

主要な操作の流れは、「ページを開く → 入力またはファイル読み込み → プレビュー確認 →（必要に応じ）出力設定 → 変換 → ダウンロード」という直線的な流れであり、各ステップは任意に行き来できる。詳細なワイヤーフレームは設計フェーズで別途作成する。

---

## 9. データ要件

本システムは、利用者の文書を永続的に保存しないことを基本方針とする。ただし利便性のため、ブラウザのローカル領域に下書き（入力中の Markdown と出力設定）を一時的に保持し、利用者が任意に消去できるものとする。サーバー側で変換を行う場合、受け取った文書はメモリ上でのみ処理し、生成完了後に破棄する。永続的に管理するのは、文書内容を含まない匿名の利用統計（変換回数・エラー率など）に限る。これにより、個人情報・機微情報を保持しない設計とする。

---

## 10. 外部ライブラリ・依存要素

本システムは以下の種類の構成要素に依存する。具体的な選定は技術調査を経て確定する。Markdown 構文解析には CommonMark/GFM 準拠のパーサ（例: markdown-it）を用いる。コードのシンタックスハイライトにはハイライトライブラリ（例: highlight.js / Shiki）、数式描画には数式組版ライブラリ（例: KaTeX）、ダイアグラムには Mermaid を利用する。HTML サニタイズには専用ライブラリを用いる。PDF 生成の方式は第11章のとおりであり、サーバー側変換を採る場合はヘッドレスブラウザ（例: Puppeteer / Chromium）を、クライアント側変換を採る場合はページ分割ライブラリ（例: paged.js）等を用いる。日本語表示のため、CJK 対応フォントを同梱・埋め込み可能とする。

## 11. システム構成・技術スタック案（変換方式の設計判断）

本プロダクトの技術的中核は「Markdown をどこで PDF に変換するか」という設計判断であり、二つの方式が考えられる。

**方式A：クライアント側変換（ブラウザ内完結）。** 文書がブラウザの外へ出ないためプライバシー上の優位が大きく、サーバー処理コストもかからず容易にスケールする。一方で、厳密なページ分割やヘッダー/フッター、ページ番号などの組版精度はサーバー方式に劣る場合がある。

**方式B：サーバー側変換（ヘッドレスブラウザによる描画）。** ヘッドレス Chromium で HTML を描画し PDF 化するため、CSS のページメディア仕様を活かした高品質な出力が得られ、利用者間で結果が安定する。一方で、文書がサーバーを経由するためプライバシー設計（非保持・即時破棄・無記録）を厳格に行う必要があり、サーバーコストとスケーリング対策を要する。

**MVP 実装方針（現リポジトリ）。** 本リポジトリの第1フェーズ実装では、検証容易性と即時公開可能性を優先し、まず**クライアント側変換（方式A）**を採用する。具体的には、ブラウザのネイティブな「印刷 → PDF として保存」機能を `window.print()` から起動し、専用の印刷用CSS（`@page` でサイズ・余白・向きを制御）に基づいて高品質な出力を得る。これにより、文書はブラウザ外に一切出ず、本文テキストは選択・検索可能であり、CJK フォントは OS 側のフォントが利用されるため文字崩れも生じない。サーバー側変換（方式B）は第2フェーズ以降の選択肢として残す。

技術スタックの一案として、フロントエンドは React（TypeScript）によるシングルページアプリケーション、エディタは CodeMirror 等を用いる。サーバー側変換を採る場合のバックエンドは Node.js（TypeScript）＋ Puppeteer（Chromium）とする。配信は CDN とし、変換 API はコンテナ化してクラウドに展開する。CI/CD・監視・エラートラッキングを標準で整備する。

## 12. 制約・前提条件

本システムは、対応ブラウザを備えた環境での利用を前提とする。入力は Markdown（CommonMark/GFM を基準）に限る。生成 PDF の体裁は、対応するテーマと CSS の範囲で表現できるものに限られ、任意のレイアウトを完全に再現するものではない。外部 URL の画像はネットワーク到達性に依存する。日本語以外の言語・文字体系については、対応フォントの範囲で表示する。

---

## 13. リスクと対応方針

主要なリスクとして、まず**日本語・CJK フォントの埋め込み不良による文字崩れ**が挙げられる。これは既存ツールで頻発する品質問題であり、対応フォントの同梱と埋め込み検証、代表文書での出力テストを徹底する。次に**プライバシーへの不安**については、非保持・即時破棄・無記録の方針を明示し、可能な範囲でクライアント側変換も提供することで信頼を確保する。**入力起因のセキュリティリスク**（不正なHTML・スクリプト）については、サニタイズとサンドボックス化で対応する。**大容量文書による処理遅延・負荷**については、サイズ上限・タイムアウト・進捗表示・水平スケールで備える。**ライブラリ依存による描画差異**については、対象記法のテストケースを整備し回帰を検知する。

## 14. リリース計画（フェーズ）

第1フェーズ（MVP）では、優先度「Must」を中心に、テキスト入力・ファイル読み込み、リアルタイムプレビュー（CommonMark/GFM・コードハイライト・画像）、PDF 変換とダウンロード、用紙サイズ・向き・余白の指定、CJK 対応フォントの埋め込み、レスポンシブ対応とエラー通知を実装する。Markdown を崩れなく PDF 化できる基本価値を成立させる。

第2フェーズでは、テーマ選択、ヘッダー/フッターとページ番号、目次生成、数式表示、フロントマター、改ページ制御、ファイル名指定など「Should」を拡充し、配布用途に耐える体裁を整える。

第3フェーズ以降では、Mermaid 図、カスタムCSS、表紙生成、多言語UI、クライアント側変換モード、記法ガイド、下書きの自動保持などの拡張を検討する。

## 15. リポジトリ情報

ご指定のとおり、本システムのリポジトリ名は **Matop** とする。

### 15.1 リポジトリ名

リポジトリ名は `Matop`（URL・パッケージ上は小文字の `matop`）とする。名称は **Ma**rkdown **to** **P**df に由来し、プロダクトの機能を端的に表す。

### 15.2 ブランチ・コミット規約

ブランチ戦略は `main`（本番）を基本とし、機能開発は `feature/*`、不具合修正は `fix/*` を切る軽量な GitHub Flow を推奨する。コミットメッセージは Conventional Commits（`feat:`、`fix:`、`docs:` 等）に従う。
